# Потоки данных и логика разделения на домены

### Сценарий 1: ИИ-анализ медицинских данных

**Участники:** Clinical Domain → Integration Layer → AI/Medical Domain

**Поток:**

1. Оператор клиники фиксирует визит пациента в EMR System.
2. Врач инициирует запрос на ИИ-диагностику через Clinical API.
3. Clinical API обращается к API Gateway (Integration Layer) — синхронный вызов.
4. API Gateway маршрутизирует запрос в AI Service API.
5. AI Service API забирает снимки из PHI Vault напрямую по зашифрованному каналу — PHI не проходит через шину и не попадает в Data Platform.
6. ML-модели возвращают результат диагностики обратно через API Gateway → Clinical API → врачу.
7. Агрегированный результат (без PHI) публикуется в Event Bus → Data Lakehouse для аналитики нагрузки ИИ-сервисов.

**Бизнес-ценность:** врач получает результат диагностики в рамках одного визита, а не на следующий день. ИИ-домен развивается независимо — обновление модели не требует изменений в Clinical Domain.

### Сценарий 2: Интеграция нового финтех-сервиса с клиниками

**Участники:** Fintech Domain → Integration Layer → Clinical Domain

**Поток:**

1. Клиент банка оплачивает медицинские услуги через Fintech API.
2. Banking Core инициирует запрос к API Gateway для получения данных о визите (сумма, дата, код услуги) — без PHI.
3. API Gateway маршрутизирует запрос к Clinical API.
4. Clinical API возвращает агрегированные данные визита (только то, что разрешено доменным контрактом).
5. Fintech Domain формирует платёжный документ и проводит транзакцию.
6. Payment Service публикует событие о транзакции в Event Bus.
7. Fraud Detection подписан на поток транзакций и скорит каждую в реальном времени.

**Бизнес-ценность:** финтех и клиники обмениваются только контрактными данными. Clinical Domain не знает о деталях банковской логики — оба домена могут выпускать релизы независимо.

---

### Сценарий 3: Подключение нового бизнес-домена (фармацевтика)

**Участники:** New Business Domain → Integration Layer → Data Platform + другие домены

**Поток:**

1. Новый домен регистрируется в API Gateway — публикует спецификацию своего API и схему событий в Schema Registry.
2. Domain API начинает публиковать события в Event Bus (например, данные о наличии препаратов, поставках).
3. Kafka Connect автоматически стримит события в Data Lakehouse.
4. dbt-трансформации подхватывают новую таблицу событий и строят витрину для нового домена.
5. Бизнес-пользователи получают данные нового домена в Self-Service Portal без участия IT.
6. Clinical Domain может подписаться на события фармацевтики (наличие препаратов) через Event Bus.

**Бизнес-ценность:** подключение нового домена не требует изменений в ядре архитектуры. Стандартный контракт (API + Kafka schema) позволяет онбордить новый бизнес за недели вместо месяцев.

---

### Сценарий 4: Быстрая подготовка управленческой отчётности

**Участники:** Все домены → Integration Layer → Data Platform → Бизнес-пользователь

**Поток:**

1. Все домены публикуют события в Event Bus через CDC (Change Data Capture) или прямые Kafka Producer.
2. Kafka Connect стримит события в Data Lakehouse (Apache Iceberg).
3. dbt запускает трансформации по расписанию (или инкрементально) — строит логические витрины по доменам.
4. Semantic Layer экспонирует единые бизнес-метрики с RBAC.
5. Бизнес-пользователь открывает Self-Service Portal, выбирает нужные срезы и получает отчёт за секунды.

**Бизнес-ценность:** отчёт формируется из преагрегированных витрин Lakehouse, а не из сырого DWH. Время — секунды вместо часов. Управленческие решения принимаются на актуальных данных.

## 2. Логика разделения на домены

### Принцип разделения

Границы доменов проведены по принципу **бизнес-возможности (business capability)**: каждый домен владеет данными и логикой одной бизнес-функции и не зависит от внутреннего устройства других доменов.

| Домен        | Бизнес-возможность                | Владеет данными                       |
| ------------ | --------------------------------- | ------------------------------------- |
| Clinical     | Оказание медицинской помощи       | Пациенты, расписание, инвентарь, PHI  |
| AI/Medical   | Интеллектуальный анализ медданных | Модели, результаты инференса          |
| Fintech      | Банковские и финансовые сервисы   | Счета, кредиты, транзакции            |
| Corporate    | Управление группой компаний       | KPI, HR, консолидированная отчётность |
| New Business | Новые направления (plug-in)       | Данные домена изолированы             |

Каждый домен публикует **публичный контракт** (Domain API + Kafka schema) и скрывает внутреннюю реализацию. Это гарантирует, что изменение внутри домена не ломает других.

---

### Преимущества для бизнеса

#### Ускорение вывода продуктов на рынок (time-to-market)

В текущей архитектуре любая доработка под нужды банка или ИИ-сервисов требует изменений в общей схеме DWH и согласования со всеми командами. Цикл релиза — месяцы.

После разделения на домены:

- Fintech Domain выпускает новый кредитный продукт, не затрагивая Clinical Domain.
- AI/Medical Domain обновляет ML-модель, не согласовывая изменения с банком.
- Новый бизнес-партнёр подключается через стандартный контракт, не блокируя другие команды.

Каждый домен живёт по своему циклу релизов. Time-to-market сокращается с месяцев до недель.

#### Снижение зависимости от DWH

Сейчас DWH является единственным источником данных для всех потребителей: BI, ИИ-сервисов, финтеха и операционных систем. Любой сбой или деградация DWH останавливает весь бизнес.

После трансформации:

- Каждый домен имеет собственную операционную БД — падение DWH не влияет на обслуживание пациентов и банковские операции.
- Data Platform (Lakehouse) заменяет DWH как источник аналитики и масштабируется независимо от операционных систем.
- Бизнес-логика вынесена из DWH в сервисы доменов — изменение логики не требует изменений в хранилище.

#### Возможность отдельного развития направлений

| Аспект                     | AS-IS (единый DWH)              | TO-BE (домены)                                             |
| -------------------------- | ------------------------------- | ---------------------------------------------------------- |
| Релиз новой фичи           | Согласование со всеми командами | Независимый релиз внутри домена                            |
| Масштабирование            | Весь сервер целиком             | Только нужный домен                                        |
| Найм и технологии          | Единый стек для всех            | Каждый домен выбирает свой стек                            |
| Регуляторные аудиты        | Аудит всей системы целиком      | Аудит только нужного домена (банк — только Fintech Domain) |
| Подключение нового бизнеса | Изменения в общей схеме DWH     | Регистрация через стандартный контракт                     |

#### Соответствие регуляторным требованиям

Изоляция доменов решает сразу две регуляторные проблемы:

- **152-ФЗ** — PHI физически изолированы в PHI Vault внутри Clinical Domain, не попадают в Data Platform и недоступны другим доменам.
- **Требования ЦБ к банкам** — Fintech Domain изолирован, банковские данные не смешиваются с медицинскими. Аудит банка затрагивает только Fintech Domain.
