# Бизнес-обоснование этапов трансформации

## Фаза 0 — Фундамент и комплаенс (Месяц 1–2)

### Аудит данных в DWH

Без инвентаризации DWH каждое последующее решение принимается вслепую. Команды не знают, какие данные существуют, кто их использует и что сломается при миграции. Аудит занимает 3–4 недели, но предотвращает ситуацию, когда критичный отчёт перестаёт работать через месяц после «успешной» миграции.

| Измерение           | Влияние                                                       |
| ------------------- | ------------------------------------------------------------- |
| 🕐 Скорость решений | Нейтральное на этом этапе — инвестиция в будущее              |
| 🏥 Качество сервиса | Предотвращает потерю данных при миграции                      |
| 💰 Снижение затрат  | Экономит 2–3 месяца разработки за счёт понимания зависимостей |
| 📈 Масштабирование  | Без карты данных невозможно правильно разграничить домены     |

---

### Определение границ доменов

Это самое дешёвое решение из всех: несколько воркшопов с командами. Цена ошибки — полная переработка архитектуры через полгода. Если границы доменов проведены неверно, Fintech Domain будет постоянно «ходить» за данными в Clinical Domain, и независимости не получится.

| Измерение           | Влияние                                                                  |
| ------------------- | ------------------------------------------------------------------------ |
| 🕐 Скорость решений | Ускоряет согласование архитектуры — все команды работают по единой карте |
| 🏥 Качество сервиса | Правильные границы = правильная изоляция = меньше инцидентов на стыках   |
| 💰 Снижение затрат  | Предотвращает дорогостоящий рефакторинг через 6–12 месяцев               |
| 📈 Масштабирование  | Чёткие границы — единственный способ добавлять новые домены без хаоса    |

---

### Комплаенс-аудит: 152-ФЗ и требования ЦБ

Это не «лучшая практика» — это юридическое обязательство, нарушение которого уже происходит. Медицинские и финансовые данные смешаны в одном DWH прямо сейчас. При проверке регулятором компания не сможет доказать ни изоляцию PHI, ни разграничение банковских данных.

**Конкретные риски без этого шага:**

- Штрафы по 152-ФЗ
- Приостановка банковских операций до устранения нарушений
- Репутационный ущерб при публичном инциденте с утечкой медданных

| Измерение           | Влияние                                                             |
| ------------------- | ------------------------------------------------------------------- |
| 🕐 Скорость решений | Нейтральное — но отсутствие этого шага может остановить весь бизнес |
| 🏥 Качество сервиса | Критично: нарушение = возможная остановка банковских сервисов       |
| 💰 Снижение затрат  | Предотвращает штрафы, которые могут превышать годовой IT-бюджет     |
| 📈 Масштабирование  | Без комплаенса нельзя легально масштабировать обработку медданных   |

---

### Выбор облачного провайдера и PoC

Переход в облако — необратимое решение с последствиями на 5–10 лет. PoC с реальной нагрузкой стоит 2–3 недели инженерного времени. Ошибка выбора провайдера может стоить года работы и миграции между облаками.

| Измерение           | Влияние                                                                                   |
| ------------------- | ----------------------------------------------------------------------------------------- |
| 🕐 Скорость решений | Нейтральное сейчас — критично для скорости всех последующих этапов                        |
| 🏥 Качество сервиса | PoC подтверждает, что SLA облака соответствует требованиям медицины и банка               |
| 💰 Снижение затрат  | Правильный выбор экономит 20–40% стоимости облака на горизонте 3 лет                      |
| 📈 Масштабирование  | Managed cloud-сервисы — единственный способ масштабироваться без роста on-premise команды |

## Фаза 1 — Инфраструктура и изоляция (Месяц 3–5)

### PHI Vault: физическая изоляция медицинских данных

Это первый шаг, который создаёт реальную бизнес-ценность: после изоляции PHI компания получает юридическую защиту, а Data Platform — возможность безопасно работать с данными клиник. Без PHI Vault портал самообслуживания нельзя запустить: он будет либо не иметь доступа к клиническим данным вообще, либо нарушать 152-ФЗ.

**Прямой бизнес-эффект:** ИИ-сервисы получают доступ к снимкам через безопасный API и могут начать приносить ценность — быстрая диагностика, снижение нагрузки на врачей, меньше ошибок постановки диагноза.

| Измерение           | Влияние                                                                            |
| ------------------- | ---------------------------------------------------------------------------------- |
| 🕐 Скорость решений | Разблокирует аналитику клинических данных (без PHI) для управленческих отчётов     |
| 🏥 Качество сервиса | Исключает риск несанкционированного доступа к данным пациентов                     |
| 💰 Снижение затрат  | Устраняет регуляторные штрафы; снижает стоимость страхования данных                |
| 📈 Масштабирование  | Открывает возможность подключения новых ИИ-моделей без изменений в Clinical Domain |

---

### Kafka: замена монолитной ESB

Apache Camel ESB — единственная шина для всех интеграций. Её сбой парализует обмен данными между клиниками, банком и ИИ-сервисами одновременно. Kafka разделяет потоки: сбой в одном домене не влияет на других.

**Конкретный пример:** сейчас если ESB перегружена запросами от BI-отчётов, медицинские снимки не передаются в ИИ-сервисы вовремя. После перехода на Kafka каждый поток независим — отчётность не влияет на диагностику.

| Измерение           | Влияние                                                                     |
| ------------------- | --------------------------------------------------------------------------- |
| 🕐 Скорость решений | Данные из всех доменов начинают течь в Lakehouse в реальном времени         |
| 🏥 Качество сервиса | Устраняет единую точку отказа; инциденты в одном домене не блокируют другие |
| 💰 Снижение затрат  | Снижает стоимость поддержки ESB; уменьшает количество инцидентов            |
| 📈 Масштабирование  | Новый домен публикует события в Kafka без изменений в шине                  |

---

### Data Lakehouse: первый слой аналитических данных

Это инфраструктурная инвестиция без немедленной видимой бизнес-ценности — но она открывает все последующие: портал, быстрые отчёты, аналитика новых доменов. Без Lakehouse портал строить не на чём.

**Ключевое отличие от старого DWH:** Lakehouse принимает данные из Kafka в реальном времени. Отчёт за вчера — не через 8 часов после полуночного ETL, а через 5 минут после события.

| Измерение           | Влияние                                                                                 |
| ------------------- | --------------------------------------------------------------------------------------- |
| 🕐 Скорость решений | Данные актуальны с задержкой минуты, а не часы                                          |
| 🏥 Качество сервиса | ACID-транзакции и time travel обеспечивают корректность данных                          |
| 💰 Снижение затрат  | Колоночное хранилище снижает стоимость хранения на 40–60% vs row-based SQL Server       |
| 📈 Масштабирование  | Горизонтальное масштабирование — добавляем вычислительные ресурсы, не меняя архитектуру |

---

### Изоляция Fintech-домена и RBAC

Банк внутри холдинга — отдельное регулируемое юридическое лицо. ЦБ требует, чтобы банковские данные были изолированы от других систем группы. Смешение с медицинскими данными — нарушение, при котором банк может лишиться лицензии.

После изоляции финтех-команда получает свою БД и перестаёт конкурировать за ресурсы общего DWH. Это первый шаг к тому, чтобы банк мог выпускать новые продукты независимо.

| Измерение           | Влияние                                                                  |
| ------------------- | ------------------------------------------------------------------------ |
| 🕐 Скорость решений | Финтех-аналитика перестаёт тормозить из-за конкуренции за ресурсы DWH    |
| 🏥 Качество сервиса | Банковские операции не деградируют во время пиков аналитической нагрузки |
| 💰 Снижение затрат  | Устраняет регуляторный риск потери банковской лицензии                   |
| 📈 Масштабирование  | Fintech DB масштабируется независимо от других доменов                   |

## Фаза 2 — Самообслуживание и независимость (Месяц 6–9)

### Semantic Layer: единые бизнес-метрики

Сейчас в компании нет единого ответа на вопрос «какова наша выручка за квартал?». Финансовый директор, директор клиник и директор банка считают её по-разному, потому что каждый пишет свои SQL-запросы к DWH. Согласование занимает дни.

Semantic Layer фиксирует одно определение «выручки» (и 20–30 других ключевых метрик) — и все пользователи видят одно число. Конец спорам о данных на совещаниях.

| Измерение           | Влияние                                                                     |
| ------------------- | --------------------------------------------------------------------------- |
| 🕐 Скорость решений | Устраняет 2–4 часа согласования цифр перед каждым важным совещанием         |
| 🏥 Качество сервиса | Единые метрики исключают управленческие решения на основе неверных данных   |
| 💰 Снижение затрат  | Сокращает количество аналитиков, занятых «объяснением расхождений»          |
| 📈 Масштабирование  | Новый домен добавляет свои метрики в общий каталог — без кастомных запросов |

---

### Self-Service Portal Beta

Сейчас цепочка «нужен отчёт → задача аналитику → очередь → SQL-запрос → проверка → результат» занимает от нескольких дней до недели. При срочных управленческих решениях (конкурент снизил цены, аномальный отток пациентов) это критически много.

После запуска портала менеджер получает ответ за 2–5 минут, не завися от занятости аналитика. Аналитики освобождаются для стратегических задач вместо генерации рутинных отчётов.

**Измеримый результат:** если отдел аналитики тратит 40% времени на рутинные отчёты (типичная цифра для компаний такого размера), портал возвращает эти 40% на задачи с реальной ценностью.

| Измерение           | Влияние                                                                 |
| ------------------- | ----------------------------------------------------------------------- |
| 🕐 Скорость решений | Время получения отчёта: с 2–5 дней до 2–5 минут                         |
| 🏥 Качество сервиса | Менеджеры клиник видят загрузку и проблемы в реальном времени           |
| 💰 Снижение затрат  | 40% времени аналитиков перераспределяется на задачи с более высоким ROI |
| 📈 Масштабирование  | Новые пользователи и домены подключаются без изменений в IT             |

---

### API Gateway: замена ESB для синхронных вызовов

ESB обрабатывает синхронные вызовы между сервисами централизованно. Это создаёт bottleneck: при высокой нагрузке ESB замедляет всех. API Gateway маршрутизирует каждый вызов напрямую к нужному сервису с минимальной задержкой.

**Shadow mode критичен:** клиники и банк работают 24/7. Нельзя позволить переключению с ESB на Gateway привести к даже минутному недоступности сервисов.

| Измерение           | Влияние                                                                    |
| ------------------- | -------------------------------------------------------------------------- |
| 🕐 Скорость решений | API-вызовы между доменами быстрее за счёт устранения ESB как посредника    |
| 🏥 Качество сервиса | Каждый домен имеет собственный circuit breaker; сбой одного не каскадирует |
| 💰 Снижение затрат  | Снижение стоимости поддержки ESB; rate-limiting защищает от перегрузки     |
| 📈 Масштабирование  | Новый домен регистрируется в Gateway за часы, а не недели как в ESB        |

---

### Независимость ИИ-домена

Сейчас обновление ML-модели требует координации с Clinical Domain (доступ к данным) и Data Platform (обновление пайплайнов в DWH). Цикл — месяц. После изоляции ИИ-команда обновляет модель за день: забирает данные из PHI Vault напрямую, деплоит через MLflow, мониторит качество автоматически.

**Бизнес-эффект:** точность диагностики растёт быстрее, потому что модели обновляются чаще. Конкурентное преимущество в ИИ-медицине напрямую зависит от скорости итераций.

| Измерение           | Влияние                                                                                        |
| ------------------- | ---------------------------------------------------------------------------------------------- |
| 🕐 Скорость решений | Цикл обновления модели: с месяца до дней                                                       |
| 🏥 Качество сервиса | Более актуальные модели = более точная диагностика                                             |
| 💰 Снижение затрат  | Меньше координации между командами = меньше потерь на межкомандные согласования                |
| 📈 Масштабирование  | Добавление новой специализации (кардиология, онкология) не требует изменений в Clinical Domain |

---

### Независимость Fintech-домена

После изоляции БД (Фаза 1) финтех-команда получает независимый цикл релизов. Новый кредитный продукт или изменение тарифов больше не требуют «окна релиза» совместно с клиниками или ИИ-командой.

**Измеримый эффект:** банки с независимыми командами выпускают новые продукты в 3–5 раз быстрее, чем банки с монолитной архитектурой. В конкурентной среде это напрямую влияет на долю рынка.

| Измерение           | Влияние                                                                       |
| ------------------- | ----------------------------------------------------------------------------- |
| 🕐 Скорость решений | Новый финансовый продукт: с 3 месяцев до 2–4 недель                           |
| 🏥 Качество сервиса | Fraud Detection в реальном времени снижает финансовые потери от мошенничества |
| 💰 Снижение затрат  | Меньше координации при релизах; Fraud Detection снижает потери от фрода       |
| 📈 Масштабирование  | Каждый новый финансовый продукт — независимый сервис, не затрагивающий других |

## Фаза 3 — Масштабирование и вывод Legacy (Месяц 10–12)

> _«Legacy не уходит сам. Его нужно выключить сознательно, когда альтернатива полностью готова.»_

### Self-Service Portal Production

Beta подтвердила концепцию и выявила узкие места. Production-запуск — это rollout на всех 100+ бизнес-пользователей с SLA на время ответа. Ключевое изменение: IT перестаёт быть посредником между данными и решениями.

**Накопленный эффект к этому моменту:** данные актуальны (Lakehouse + Kafka), метрики единые (Semantic Layer), доступ разграничен (RBAC). Портал работает на всей этой инфраструктуре.

| Измерение           | Влияние                                                                              |
| ------------------- | ------------------------------------------------------------------------------------ |
| 🕐 Скорость решений | Любой руководитель получает любой срез данных за секунды в любое время               |
| 🏥 Качество сервиса | Директор клиники видит отклонения в загрузке в реальном времени — быстрее реагирует  |
| 💰 Снижение затрат  | ROI портала: стоимость лицензий BI-инструментов vs. высвобождение времени аналитиков |
| 📈 Масштабирование  | Новый домен = автоматически новые данные в портале без доработки                     |

### Вывод SQL Server 2008 и ESB

Каждый месяц работы SQL Server 2008 — это:

- Стоимость поддержки on-premise железа и лицензий
- Риск неисправимого сбоя (EOL оборудование и ПО)
- Ограничение производительности всех систем, подключённых к нему
- Отсутствие патчей безопасности с 2019 года

После вывода компания сокращает операционные затраты на инфраструктуру на 30–40% и устраняет крупнейший источник технического долга и риска.

| Измерение           | Влияние                                                                     |
| ------------------- | --------------------------------------------------------------------------- |
| 🕐 Скорость решений | Устраняется главный bottleneck производительности аналитики                 |
| 🏥 Качество сервиса | Исчезает риск отказа критической инфраструктуры без возможности починки     |
| 💰 Снижение затрат  | -30–40% операционных затрат на инфраструктуру; устранение страхового риска  |
| 📈 Масштабирование  | Больше нет потолка масштабирования, обусловленного ресурсами одного сервера |

### Онбординг новых бизнес-доменов

Стандартный онбординг-контракт — это продукт для будущих партнёров компании. Фармацевтическая компания или производитель медоборудования получают инструкцию: как опубликовать события, как зарегистрироваться в Schema Registry, как данные появятся в аналитике.

**Бизнес-модель:** «Будущее 2.0» создаёт экосистему, в которой ценность платформы растёт с каждым новым участником. Это меняет позицию компании с «поставщика медицинских услуг» на «оператора медицинской экосистемы».

| Измерение           | Влияние                                                                   |
| ------------------- | ------------------------------------------------------------------------- |
| 🕐 Скорость решений | Данные нового партнёра появляются в аналитике через 2–4 недели            |
| 🏥 Качество сервиса | Больше данных о пациенте (препараты, оборудование) = более полная картина |
| 💰 Снижение затрат  | Стандартный онбординг в 5–10 раз дешевле кастомной интеграции             |
| 📈 Масштабирование  | Линейный рост числа партнёров без нелинейного роста затрат на интеграцию  |

### Замена PowerBuilder: EMR System

PowerBuilder откладывается в последнюю фазу сознательно: это самая дорогая и долгая замена с наименьшим краткосрочным ROI. Но к Фазе 3 инфраструктура готова: PHI Vault, Clinical API, ИИ-сервисы работают. EMR встаёт поверх готового фундамента.

**Бизнес-эффект, который невозможно достичь раньше:** ИИ-диагностика встроена в рабочее место врача. Снимок → анализ модели → результат прямо в интерфейсе, без переключения между системами. Это не просто удобство — это сокращение времени от снимка до диагноза.

| Измерение           | Влияние                                                                              |
| ------------------- | ------------------------------------------------------------------------------------ |
| 🕐 Скорость решений | Врач видит результат ИИ-диагностики прямо в интерфейсе — без ручного переноса данных |
| 🏥 Качество сервиса | Снижение времени постановки диагноза; меньше ошибок из-за ручного ввода              |
| 💰 Снижение затрат  | Нет затрат на поддержку PowerBuilder и поиск редких специалистов                     |
| 📈 Масштабирование  | Новые функции (телемедицина, мобильный доступ) добавляются в современный стек        |

| Подключение нового бизнес-домена           | 3–6 месяцев      | 2–4 недели            |
| Операционные затраты на инфраструктуру     | 100% (baseline)  | ~60–70%               |

# Обоснование решений роадмапа

## Почему именно такая последовательность фаз

Фазы выстроены по принципу **«сначала убрать риск, потом строить ценность»**. Запустить портал самообслуживания без изоляции данных — значит создать инструмент, который нарушает 152-ФЗ в момент запуска. Поэтому регуляторные блоки идут первыми, а бизнес-ценность (портал, независимость) — после закладки фундамента.

---

## Фаза 0: Фундамент и комплаенс

### Почему начинаем с аудита DWH, а не с разработки?

DWH — чёрный ящик. В нём 15+ лет бизнес-логики в хранимых процедурах, триггерах и представлениях. Без инвентаризации любая миграция — слепой перенос данных с непредсказуемым результатом. Аудит занимает 3–4 недели, но экономит 3–4 месяца разработки в будущем за счёт понимания зависимостей.

### Почему комплаенс-аудит в Фазе 0, а не в конце?

Потому что регуляторные нарушения уже существуют — сейчас, не после трансформации. Если ЦБ или Роскомнадзор инициирует проверку до завершения трансформации, последствия (штрафы, отзыв лицензии) остановят весь бизнес. Задокументировать текущее состояние и иметь утверждённый план устранения — это юридическая защита на период трансформации.

### Почему PoC облачного стека в Фазе 0?

Выбор облачного провайдера — необратимое решение с последствиями на годы. PoC с реальными данными (пусть и синтетическими) выявляет проблемы производительности и совместимости до того, как в новый стек вложены месяцы разработки. Стоимость PoC — несколько недель работы двух инженеров. Стоимость ошибки выбора провайдера — миграция через год.

---

## Фаза 1: Инфраструктура и изоляция

### Почему PHI Vault — первый приоритет Фазы 1?

Пока PHI хранятся в общем DWH, любой аналитик с доступом к DWH потенциально видит медицинские карты. Это нарушение 152-ФЗ, которое существует прямо сейчас. Изоляция PHI — не опциональное архитектурное улучшение, а юридическое обязательство. Её выполнение блокирует не только регуляторный риск, но и открывает возможность безопасного запуска портала: без PHI Vault портал нельзя запустить без нарушений.

### Почему Kafka раньше, чем API Gateway?

Kafka решает задачу стриминга данных в Lakehouse — без неё аналитическая платформа не получает данные. API Gateway решает задачу синхронных межсервисных вызовов — это нужно позже, когда домены уже работают независимо. Kafka — инфраструктурный фундамент для аналитики; Gateway — инструмент изоляции интеграций. Правильная последовательность: сначала данные течут в Lakehouse, потом убираем ESB.

### Почему изоляция Fintech-домена в Фазе 1, а не позже?

Банковская лицензия требует изоляции данных как базового условия. Смешение финансовых данных с медицинскими и операционными в одной БД — прямое нарушение требований ЦБ. Чем дольше финтех остаётся в общем DWH, тем выше риск регуляторных санкций. Кроме того, изолированный Fintech Domain — предпосылка для независимого цикла релизов банка (Фаза 2).

---

## Фаза 2: Самообслуживание и независимость

### Почему Semantic Layer перед запуском портала?

Портал без семантического слоя — это просто SQL-редактор с красивым интерфейсом. Бизнес-пользователи не пишут SQL. Semantic Layer переводит технические метрики (SUM(amount) WHERE status='paid') в понятные термины («выручка»). Без него портал будут использовать только аналитики, а не менеджеры — то есть основная цель не будет достигнута.

### Почему API Gateway в shadow mode 1 месяц?

ESB Apache Camel обслуживает все текущие интеграции. Мгновенное переключение с ESB на Gateway — высокий риск остановки операционных сервисов (клиники, банк). Shadow mode позволяет Gateway обрабатывать те же запросы параллельно с ESB без влияния на prod, выявить расхождения в поведении и переключиться с нулевым downtime.

### Почему независимость ИИ-домена именно в Фазе 2?

В Фазе 1 PHI Vault уже готов — ИИ-сервисы получают доступ к снимкам через защищённый API. Это разблокирует независимость ИИ: теперь ИИ-команда может обновлять модели, не затрагивая Clinical Domain. Запускать независимость ИИ раньше — до PHI Vault — означает либо блокировать ИИ-диагностику, либо нарушать изоляцию данных.

### Почему Fintech-независимость в той же Фазе 2, что и портал?

Это параллельные треки с разными командами. Fintech Domain работает над Banking Core и Fraud Detection, Data Platform — над порталом. Между ними нет зависимости: Fintech публикует события в Kafka (готова с Фазы 1), а портал потребляет эти события через Lakehouse. Параллельность сокращает общее время трансформации.

---

## Фаза 3: Масштабирование и вывод Legacy

### Почему вывод SQL Server 2008 в последней фазе?

Потому что его нельзя выключить раньше, чем все потребители переключились. Преждевременный вывод оставит без данных BI, ИИ-сервисы и финтех. Правильная последовательность: сначала альтернатива готова и верифицирована → потом переключение потребителей → потом вывод. Параллельная работа DWH и Lakehouse в Фазах 1–2 — страховка и инструмент валидации.

### Почему EMR (замена PowerBuilder) только в Фазе 3?

PowerBuilder — дорогая и долгая замена, требующая участия всех клиник и переобучения персонала. Начинать с неё — значит тратить ресурсы на проект с длительным ROI, откладывая критические задачи (PHI, изоляция, портал). В Фазе 3 уже готовы PHI Vault и Clinical API — EMR просто встаёт поверх готовой инфраструктуры, а не строит её с нуля.

### Почему онбординг новых доменов в Фазе 3, а не раньше?

Новый домен (фармацевтика, производитель оборудования) должен подключаться к стабильной инфраструктуре: Kafka работает, Lakehouse принимает данные, API Gateway настроен. Подключать новые домены к инфраструктуре в процессе строительства — значит создавать зависимость между строительством и эксплуатацией. Фаза 3 — первый момент, когда платформа достаточно стабильна для новых потребителей.

## Сквозные принципы, определившие архитектуру

**Data Mesh вместо централизованной Data Platform**
Альтернатива — построить новый централизованный DWH (например, Snowflake). Это проще, но воспроизводит ту же проблему: единая точка всего, bottleneck при росте. Data Mesh распределяет ответственность и позволяет каждому домену развиваться в своём темпе. Стоимость Data Mesh выше в начале (нужна зрелость команд), но окупается при масштабировании.

**Managed cloud-сервисы вместо self-hosted**
Self-hosted Kafka и Iceberg требуют выделенной Platform Engineering команды для поддержки. Managed-сервисы переносят операционную нагрузку на провайдера. Для компании в процессе трансформации важнее скорость, чем контроль над инфраструктурой.

**Параллельная работа legacy и нового стека**
Единовременная миграция («big bang») с высоким риском: одна ошибка останавливает весь бизнес. Параллельная работа позволяет проверить Lakehouse на реальных данных до отключения DWH и откатиться при проблемах.

**Стандартный онбординг-контракт для новых доменов**
Каждый новый бизнес-партнёр (фармацевтика и т.д.) получает документ: «вот ваш Domain API template, вот Kafka schema contract, вот инструкция по регистрации в Schema Registry». Без стандартизации каждое подключение — кастомный проект на 2–3 месяца. Со стандартом — 2–4 недели.
